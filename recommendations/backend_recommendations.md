# Рекомендации по переносу логики на backend

Этот файл фиксирует решения, накопившиеся в ходе frontend-этапов 1–22, которые были закрыты или смягчены на frontend, но архитектурно надёжнее реализовать или дополнительно защитить на backend.

Текущие frontend-исправления удалять не нужно до появления соответствующей backend-реализации.

## 1. Атомарное создание теста вместе с назначениями

**Связано с этапом 11.**

### Текущее решение

Frontend выполняет последовательность:

1. `POST /tests`
2. несколько `POST /tests/{testId}/assignments`
3. при ошибке — компенсирующий `DELETE /tests/{testId}`

Это уменьшает риск частично сохранённых данных, но не является настоящей транзакцией. Между запросами тест и часть назначений уже существуют в БД, а rollback-запрос тоже может завершиться ошибкой.

### Рекомендуемое backend-решение

Создать одну бизнес-операцию для создания теста вместе со всеми назначениями и выполнить её внутри одной Spring-транзакции:

```java
@Transactional
public TestResponse createTestWithAssignments(CreateTestRequest request) {
    // create Test
    // create all TestAssignments
    // return result
}
```

Контракт должен обеспечивать принцип:

- либо тест и все назначения созданы;
- либо не создано ничего.

После этого frontend-компенсацию через `DELETE` можно удалить.

**Приоритет: высокий.**

## 2. Не передавать студенту правильность каждого конкретного ответа

**Связано с этапом 6.**

### Текущее решение

Frontend больше не показывает студенту:

- `Верно / Неверно` по каждому вопросу;
- правильный ответ.

Однако backend всё ещё может возвращать поле `correct` в student-response. Его можно увидеть через DevTools / Network.

### Рекомендуемое backend-решение

Использовать отдельные DTO для STUDENT и TEACHER.

Для студента после попытки возвращать только разрешённую агрегированную информацию, например:

```json
{
  "attemptId": 15,
  "score": 8,
  "correctCount": 8,
  "totalQuestions": 10
}
```

Не возвращать по каждому вопросу:

- `correct`;
- `correctAnswer`;
- внутренние признаки правильного варианта.

Если по требованиям правильность разрешается показывать только после исчерпания попыток или окончания периода тестирования, это правило также должно вычисляться на backend.

**Приоритет: высокий.**

## 3. Проверять доступ студента к предмету на backend

**Связано с этапом 4.**

### Текущее решение

Student UI переведён с:

`GET /api/v1/subjects/{id}`

на:

`GET /api/v1/public/learning/subjects/{id}`

Это закрывает обычный пользовательский сценарий, но прямой REST-запрос к общему endpoint всё ещё не должен полагаться на frontend.

### Рекомендуемое backend-решение

Один из вариантов:

1. запретить STUDENT доступ к общему `GET /subjects/{id}` через `SecurityConfig`; либо
2. добавить объектную проверку принадлежности предмета текущему студенту; либо
3. оставить общий endpoint только для TEACHER/ADMIN, а STUDENT обслуживать исключительно через `/public/learning/**`.

Право доступа к данным должно проверяться на сервере независимо от того, какую страницу показывает frontend.

**Приоритет: высокий.**

## 4. Централизовать состояние готовности аккаунта

**Связано с этапами 3 и 9.**

### Текущее решение

Frontend сам вычисляет, готов ли аккаунт к работе:

- существует `personId`;
- назначена одна из ролей `STUDENT`, `TEACHER`, `ADMIN`.

Также frontend отдельно получает флаг публичной регистрации через `VITE_PUBLIC_REGISTRATION_ENABLED`, который должен вручную совпадать с backend-настройкой `APP_PUBLIC_REGISTRATION_ENABLED`.

### Рекомендуемое backend-решение

Расширить `/auth/me` или отдельный публичный config/status endpoint полями наподобие:

```json
{
  "personId": 42,
  "roles": ["STUDENT"],
  "accountState": "ACTIVE",
  "publicRegistrationEnabled": false
}
```

Возможные `accountState`:

- `PENDING_PERSON`;
- `PENDING_ROLE`;
- `ACTIVE`;
- `DISABLED`.

Frontend тогда только отображает состояние, а не дублирует серверные правила готовности аккаунта.

Особенно полезно убрать необходимость вручную синхронизировать:

`APP_PUBLIC_REGISTRATION_ENABLED`

и

`VITE_PUBLIC_REGISTRATION_ENABLED`.

**Приоритет: средний.**

## 5. Сделать контракт старта и возобновления попытки более явным

**Связано с этапом 8.**

### Текущее решение

Frontend сохраняет завершённую попытку в `sessionStorage`, чтобы обычный F5 на странице результата не вызывал новый `POST .../attempts/start` и не расходовал следующую попытку.

Это исправляет UI-сценарий, но состояние попытки в браузере остаётся локальным.

### Рекомендуемое backend-решение

Разделить операции:

- получение текущего состояния попытки;
- возобновление незавершённой попытки;
- явный старт новой попытки.

Например:

```text
GET  /test-assignments/{id}/attempts/current
POST /test-assignments/{id}/attempts/start
```

`POST start` должен использоваться только после явного действия пользователя «Начать новую попытку».

Дополнительно можно возвращать состояние:

```json
{
  "state": "COMPLETED",
  "attemptId": 25,
  "attemptsRemaining": 2
}
```

Тогда восстановление после F5 не зависит от `sessionStorage`.

**Приоритет: средний.**

## 6. Добавить агрегированные role-aware endpoints для сложных учебных экранов

**Связано с этапами 2 и 10.**

### Текущее решение

Frontend сам собирает ADMIN/TEACHER-контекст из нескольких сущностей:

- `SubjectMembership`;
- `TeachingAssignment`;
- предметов;
- групп;
- лекций.

При нескольких преподавателях одного предмета frontend обязан самостоятельно сохранять связь с конкретным `subjectMembershipId`.

### Рекомендуемое backend-решение

Для сложных экранов нагрузки можно добавить DTO, который сразу возвращает связанный контекст, например:

```json
{
  "subjectMembershipId": 17,
  "subjectId": 5,
  "subjectName": "Базы данных",
  "teacherPersonId": 12,
  "teacherName": "Иванов И.И.",
  "groups": [],
  "lectures": []
}
```

Это не обязательная правка для корректности текущей версии, но она:

- уменьшит количество REST-запросов;
- снизит риск смешивания контекста разных преподавателей;
- упростит frontend;
- упростит regression-тесты.

**Приоритет: низкий / архитектурный.**

## 7. Явная модель делегированного авторства шаблона курса для ADMIN

**Связано с этапом 12.**

### Текущее решение

Backend при `POST /courses/templates` всегда назначает автором шаблона текущего пользователя через `currentPersonId(authentication)`. Передача `authorPersonId` с frontend не поддерживается контрактом `CourseTemplateRequest` и не должна использоваться как способ подмены автора.

Поэтому frontend в ADMIN-режиме:

- фильтрует существующие шаблоны по преподавателю из выбранного `SubjectMembership`;
- позволяет редактировать существующие шаблоны этого преподавателя;
- не позволяет создавать новый шаблон так, будто его автором является выбранный преподаватель.

### Рекомендуемое backend-решение

Если по бизнес-требованиям администратор действительно должен создавать шаблон **от имени преподавателя**, это нужно реализовать явно на backend, а не доверять произвольному `authorPersonId` из клиента.

Возможный контракт:

```json
{
  "subjectId": 5,
  "ownerPersonId": 12,
  "name": "Базовый курс",
  "publicVisible": true
}
```

Backend для ADMIN должен:

1. проверить, что `ownerPersonId` существует;
2. проверить активный преподавательский `SubjectMembership` этого пользователя для указанного предмета;
3. отдельно хранить фактического инициатора операции (`createdBy/actor`) и владельца шаблона (`author/owner`), если эти понятия должны различаться;
4. запретить такую делегацию обычному TEACHER;
5. желательно журналировать административное действие.

Если делегированное создание не является бизнес-требованием, текущая backend-модель, где автором является фактический текущий пользователь, безопаснее и должна остаться основной.

**Приоритет: средний / зависит от бизнес-требований.**

## 8. Проверять активность SubjectMembership при создании преподавательской нагрузки

**Связано с этапом 13.**

### Текущее решение

Frontend больше не предлагает для новых `TeachingAssignment` преподавательские membership, если:

- `status != 1`;
- заполнен `removedAtUtc`;
- membership не относится к роли преподавателя.

Непосредственно перед созданием нагрузки frontend повторно запрашивает актуальные membership с `activeOnly=true` и `status=1`. Если выбранного преподавателя успели деактивировать после открытия страницы, создание отменяется и пользователь должен выбрать преподавателя заново.

Исторические `TeachingAssignment` при этом продолжают отображаться даже если связанный преподавательский membership уже неактивен.

### Почему этого недостаточно

Frontend-проверку можно обойти прямым REST-запросом. Кроме того, между последней frontend-проверкой и `POST /teaching/assignments` остаётся небольшой race window.

Текущий `TeachingService.createAssignment(...)` получает `SubjectMembership` по ID, но не проверяет, что membership всё ещё активно для новых назначений.

### Рекомендуемое backend-решение

При создании нового `TeachingAssignment` backend должен требовать:

- `SubjectMembership.role == TEACHER`;
- `SubjectMembership.status == 1`;
- `SubjectMembership.removedAtUtc == null`.

Проверку лучше выполнять в самой бизнес-операции создания назначения, а не только в контроллере.

Для обновления исторического назначения правило можно применять только при смене `subjectMembershipId`, чтобы старые записи с уже закрытым membership оставались доступными для просмотра и административного завершения.

**Приоритет: высокий.**

## 9. Централизованно запрещать неактивный SubjectMembership для новых teacher-операций

**Связано с этапом 16.**

### Текущее решение

`useTeacherSubjects()` теперь разделяет два набора данных:

- все не удалённые преподавательские `SubjectMembership` сохраняются для отображения уже существующей истории и связей;
- в интерактивные селекторы для новых действий попадают только membership с `role = TEACHER`, `status = 1` и `removedAtUtc = null`.

Поэтому закрытое преподавательское назначение больше нельзя случайно выбрать на frontend для создания или изменения teacher-контента.

### Почему этого недостаточно

Это ограничение остаётся клиентским. Прямой REST-запрос может передать ID закрытого membership в backend-операцию.

В текущем backend несколько общих проверок membership в первую очередь подтверждают существование/владение записью, но не централизуют проверку `status` и `removedAtUtc` для всех mutating teacher-сценариев.

### Рекомендуемое backend-решение

Добавить единый helper уровня service/access layer, например:

```java
SubjectMembership requireActiveTeacherSubjectMembership(Integer id)
```

который требует:

- `role == TEACHER`;
- `status == 1`;
- `removedAtUtc == null`.

Использовать его во всех операциях, которые **создают или изменяют** данные в контексте конкретного `subjectMembershipId` (например, преподавательская нагрузка, лекции, темы и другие teacher-owned mutation-сценарии).

При этом read-only/history операции должны при необходимости продолжать принимать закрытые membership, чтобы старые данные не исчезали из административного просмотра.

**Приоритет: высокий.**

## 10. Сделать назначение преподавателя на предмет идемпотентной backend-операцией

**Связано с этапом 20.**

### Текущее решение

Административный frontend различает два состояния преподавательского `SubjectMembership`:

- `status = 1` — активное назначение;
- `status = 2` при `removedAtUtc = null` — приостановленное назначение, которое можно восстановить.

Если администратор снова назначает преподавателю предмет с приостановленным membership, frontend не создаёт новую запись, а вызывает обновление существующего membership со `status = 1`.

Это необходимо, потому что текущий `POST /memberships/subjects/{subjectId}` отклоняет создание новой записи, пока для той же пары `subject + person + role` существует не удалённый membership.

### Почему лучше перенести правило на backend

Семантика операции пользователя — «назначить преподавателя на предмет». Клиенту не обязательно знать, нужно ли для этого создать новую запись или реактивировать существующую. Если другой клиент не повторит frontend-логику, он получит conflict на корректной с точки зрения бизнеса операции повторного назначения.

### Рекомендуемое backend-решение

Сделать бизнес-операцию назначения идемпотентной, например внутри `MembershipService`:

1. если активный membership уже существует — вернуть его без создания дубля;
2. если существует не удалённый membership со `status = 2` — перевести его в `status = 1` и при необходимости обновить примечание;
3. если старый membership действительно удалён (`removedAtUtc != null`) — создать новую запись;
4. сохранить проверку уникальности от параллельного создания дублей.

Тогда frontend сможет вызывать одну операцию «назначить» без самостоятельной оркестрации жизненного цикла membership.

**Приоритет: средний.**

## 11. Добавить атомарные batch-операции для массовых административных изменений

**Связано с этапом 22.**

### Текущее решение

Frontend массово назначает/снимает предметы у преподавателя и добавляет/удаляет предметы факультета как набор независимых HTTP-запросов.

После этапа 22 frontend использует settled batch-flow:

- каждый элемент операции получает собственный результат;
- частичный успех не теряется;
- UI показывает количество успешных и неуспешных изменений;
- после завершения обязательно перечитывается фактическое состояние с backend.

Это делает клиент устойчивым, но не делает саму бизнес-операцию атомарной.

### Почему backend-вариант лучше

Если администратор выбирает несколько объектов как одну логическую операцию, возможен сценарий:

```text
назначение 1 -> OK
назначение 2 -> OK
назначение 3 -> ERROR
назначение 4 -> OK
```

Frontend корректно отобразит частичный результат, но данные всё равно останутся изменены частично.

Для операций, где бизнес-требование подразумевает принцип «всё или ничего», это должно решаться транзакцией на сервере.

### Рекомендуемое backend-решение

Добавить специализированные batch endpoints, например:

```text
POST   /memberships/subjects/batch-assign
POST   /memberships/subjects/batch-remove
POST   /faculties/{facultyId}/subjects/batch-add
DELETE /faculties/{facultyId}/subjects/batch-remove
```

или эквивалентные command DTO.

Сервисный метод должен выполняться внутри `@Transactional` и:

1. валидировать весь набор до изменения данных;
2. откатывать всю операцию при ошибке любого обязательного элемента;
3. возвращать структурированный результат;
4. обеспечивать защиту от дублей и параллельных конфликтов.

Если по бизнес-правилам частичный успех допустим, backend всё равно может предоставить batch endpoint с явным результатом по каждому элементу, чтобы клиент не оркестрировал десятки отдельных запросов.

**Приоритет: средний.**

# Порядок реализации

Если backend-разработку снова разрешим, рекомендуемый порядок:

1. атомарное создание теста и назначений;
2. убрать `correct`/правильные ответы из student DTO;
3. закрыть общий `/subjects/{id}` объектной авторизацией;
4. централизовать `accountState` и registration config;
5. улучшить API старта/возобновления попытки;
6. при необходимости добавить агрегированные endpoints для teacher/admin UI;
7. если это требуется бизнесом — добавить явное и аудируемое делегированное авторство шаблонов курса для ADMIN;
8. проверять активность преподавательского `SubjectMembership` при создании новой нагрузки;
9. централизовать проверку активного `SubjectMembership` для всех новых teacher mutation-операций;
10. сделать повторное назначение преподавателя на предмет идемпотентным с реактивацией приостановленного membership;
11. при необходимости добавить атомарные batch-операции для массовых административных изменений.

После реализации каждого пункта соответствующий frontend workaround следует отдельно удалить или упростить только после regression-тестов.
