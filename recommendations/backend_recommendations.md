# Рекомендации по переносу логики на backend

Этот файл фиксирует решения, которые в этапах 1–11 были закрыты или смягчены на frontend, но архитектурно надёжнее реализовать на backend.

Текущие frontend-исправления удалять не нужно до появления соответствующей backend-реализации.

## 1. Атомарное создание теста вместе с назначениями

**Связано с этапом 11.**

### Текущее решение

Frontend выполняет последовательность:

1. `POST /tests`
2. несколько `POST /tests/{testId}/assignments`
3. при ошибке — компенсирующий `DELETE /tests/{testId}`

Это уменьшает риск частично сохранённых данных, но не является настоящей транзакцией. Между запросами тест и часть назначений уже существуют в БД, а rollback-запрос тоже может завершиться ошибкой.

### Рекомендуемое backend-решение

Создать одну бизнес-операцию для создания теста вместе со всеми назначениями и выполнить её внутри одной Spring-транзакции:

```java
@Transactional
public TestResponse createTestWithAssignments(CreateTestRequest request) {
    // create Test
    // create all TestAssignments
    // return result
}
```

Контракт должен обеспечивать принцип:

- либо тест и все назначения созданы;
- либо не создано ничего.

После этого frontend-компенсацию через `DELETE` можно удалить.

**Приоритет: высокий.**

## 2. Не передавать студенту правильность каждого конкретного ответа

**Связано с этапом 6.**

### Текущее решение

Frontend больше не показывает студенту:

- `Верно / Неверно` по каждому вопросу;
- правильный ответ.

Однако backend всё ещё может возвращать поле `correct` в student-response. Его можно увидеть через DevTools / Network.

### Рекомендуемое backend-решение

Использовать отдельные DTO для STUDENT и TEACHER.

Для студента после попытки возвращать только разрешённую агрегированную информацию, например:

```json
{
  "attemptId": 15,
  "score": 8,
  "correctCount": 8,
  "totalQuestions": 10
}
```

Не возвращать по каждому вопросу:

- `correct`;
- `correctAnswer`;
- внутренние признаки правильного варианта.

Если по требованиям правильность разрешается показывать только после исчерпания попыток или окончания периода тестирования, это правило также должно вычисляться на backend.

**Приоритет: высокий.**

## 3. Проверять доступ студента к предмету на backend

**Связано с этапом 4.**

### Текущее решение

Student UI переведён с:

`GET /api/v1/subjects/{id}`

на:

`GET /api/v1/public/learning/subjects/{id}`

Это закрывает обычный пользовательский сценарий, но прямой REST-запрос к общему endpoint всё ещё не должен полагаться на frontend.

### Рекомендуемое backend-решение

Один из вариантов:

1. запретить STUDENT доступ к общему `GET /subjects/{id}` через `SecurityConfig`; либо
2. добавить объектную проверку принадлежности предмета текущему студенту; либо
3. оставить общий endpoint только для TEACHER/ADMIN, а STUDENT обслуживать исключительно через `/public/learning/**`.

Право доступа к данным должно проверяться на сервере независимо от того, какую страницу показывает frontend.

**Приоритет: высокий.**

## 4. Централизовать состояние готовности аккаунта

**Связано с этапами 3 и 9.**

### Текущее решение

Frontend сам вычисляет, готов ли аккаунт к работе:

- существует `personId`;
- назначена одна из ролей `STUDENT`, `TEACHER`, `ADMIN`.

Также frontend отдельно получает флаг публичной регистрации через `VITE_PUBLIC_REGISTRATION_ENABLED`, который должен вручную совпадать с backend-настройкой `APP_PUBLIC_REGISTRATION_ENABLED`.

### Рекомендуемое backend-решение

Расширить `/auth/me` или отдельный публичный config/status endpoint полями наподобие:

```json
{
  "personId": 42,
  "roles": ["STUDENT"],
  "accountState": "ACTIVE",
  "publicRegistrationEnabled": false
}
```

Возможные `accountState`:

- `PENDING_PERSON`;
- `PENDING_ROLE`;
- `ACTIVE`;
- `DISABLED`.

Frontend тогда только отображает состояние, а не дублирует серверные правила готовности аккаунта.

Особенно полезно убрать необходимость вручную синхронизировать:

`APP_PUBLIC_REGISTRATION_ENABLED`

и

`VITE_PUBLIC_REGISTRATION_ENABLED`.

**Приоритет: средний.**

## 5. Сделать контракт старта и возобновления попытки более явным

**Связано с этапом 8.**

### Текущее решение

Frontend сохраняет завершённую попытку в `sessionStorage`, чтобы обычный F5 на странице результата не вызывал новый `POST .../attempts/start` и не расходовал следующую попытку.

Это исправляет UI-сценарий, но состояние попытки в браузере остаётся локальным.

### Рекомендуемое backend-решение

Разделить операции:

- получение текущего состояния попытки;
- возобновление незавершённой попытки;
- явный старт новой попытки.

Например:

```text
GET  /test-assignments/{id}/attempts/current
POST /test-assignments/{id}/attempts/start
```

`POST start` должен использоваться только после явного действия пользователя «Начать новую попытку».

Дополнительно можно возвращать состояние:

```json
{
  "state": "COMPLETED",
  "attemptId": 25,
  "attemptsRemaining": 2
}
```

Тогда восстановление после F5 не зависит от `sessionStorage`.

**Приоритет: средний.**

## 6. Добавить агрегированные role-aware endpoints для сложных учебных экранов

**Связано с этапами 2 и 10.**

### Текущее решение

Frontend сам собирает ADMIN/TEACHER-контекст из нескольких сущностей:

- `SubjectMembership`;
- `TeachingAssignment`;
- предметов;
- групп;
- лекций.

При нескольких преподавателях одного предмета frontend обязан самостоятельно сохранять связь с конкретным `subjectMembershipId`.

### Рекомендуемое backend-решение

Для сложных экранов нагрузки можно добавить DTO, который сразу возвращает связанный контекст, например:

```json
{
  "subjectMembershipId": 17,
  "subjectId": 5,
  "subjectName": "Базы данных",
  "teacherPersonId": 12,
  "teacherName": "Иванов И.И.",
  "groups": [],
  "lectures": []
}
```

Это не обязательная правка для корректности текущей версии, но она:

- уменьшит количество REST-запросов;
- снизит риск смешивания контекста разных преподавателей;
- упростит frontend;
- упростит regression-тесты.

**Приоритет: низкий / архитектурный.**

## 7. Явная модель делегированного авторства шаблона курса для ADMIN

**Связано с этапом 12.**

### Текущее решение

Backend при `POST /courses/templates` всегда назначает автором шаблона текущего пользователя через `currentPersonId(authentication)`. Передача `authorPersonId` с frontend не поддерживается контрактом `CourseTemplateRequest` и не должна использоваться как способ подмены автора.

Поэтому frontend в ADMIN-режиме:

- фильтрует существующие шаблоны по преподавателю из выбранного `SubjectMembership`;
- позволяет редактировать существующие шаблоны этого преподавателя;
- не позволяет создавать новый шаблон так, будто его автором является выбранный преподаватель.

### Рекомендуемое backend-решение

Если по бизнес-требованиям администратор действительно должен создавать шаблон **от имени преподавателя**, это нужно реализовать явно на backend, а не доверять произвольному `authorPersonId` из клиента.

Возможный контракт:

```json
{
  "subjectId": 5,
  "ownerPersonId": 12,
  "name": "Базовый курс",
  "publicVisible": true
}
```

Backend для ADMIN должен:

1. проверить, что `ownerPersonId` существует;
2. проверить активный преподавательский `SubjectMembership` этого пользователя для указанного предмета;
3. отдельно хранить фактического инициатора операции (`createdBy/actor`) и владельца шаблона (`author/owner`), если эти понятия должны различаться;
4. запретить такую делегацию обычному TEACHER;
5. желательно журналировать административное действие.

Если делегированное создание не является бизнес-требованием, текущая backend-модель, где автором является фактический текущий пользователь, безопаснее и должна остаться основной.

**Приоритет: средний / зависит от бизнес-требований.**

# Порядок реализации

Если backend-разработку снова разрешим, рекомендуемый порядок:

1. атомарное создание теста и назначений;
2. убрать `correct`/правильные ответы из student DTO;
3. закрыть общий `/subjects/{id}` объектной авторизацией;
4. централизовать `accountState` и registration config;
5. улучшить API старта/возобновления попытки;
6. при необходимости добавить агрегированные endpoints для teacher/admin UI;
7. если это требуется бизнесом — добавить явное и аудируемое делегированное авторство шаблонов курса для ADMIN.

После реализации каждого пункта соответствующий frontend workaround следует отдельно удалить или упростить только после regression-тестов.
